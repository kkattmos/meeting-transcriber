     Plan: Add "only me + the bot" and "only the bot" auto-exit rules

     Context

     screen/capture.py already has a mass-exit rule that leaves the meeting when
     participant count falls below int(peak_count * 0.30) for two consecutive
     polls. It also leaves on kill sentinel, page-closed, title change, and a
     hard
     timeout.

     The bot does NOT auto-leave when the user is the only other person in a
     Google Meet call. With 2 participants (user + bot) the existing logic sees
     count=2, so is_alone = count <= 1 is False and count <= int(2 * 0.30) = 0
     is also False — nothing fires. The user tested this in a solo Meet and the
     bot stayed until the hard timeout (4h default).

     This plan adds two new rules so test calls end on their own while keeping
     the existing mass-exit path untouched. The user confirmed: keep the
     mass-exit
     rule, add a "only the bot + me" idle rule, add a "only the bot" idle rule.
     Idle timeout = 5 minutes. Tunable via env var. Leave via the in-Meet Leave
     button (consistent with the existing kill-sentinel / hard-timeout paths).

     Files to modify

     - screen/capture.py — add constants, env override, two new checks in
     wait_until_meeting_ends. Single-file change.
     - CLAUDE.md — extend the "Auto-exit policy" section to document the new
     rules, their constants, and the new env var.
     - .env.example — add IDLE_LEAVE_MINUTES=5 with a comment.

     Design

     New constants at the top of screen/capture.py

     Mirror the existing MAX_MEETING_SECONDS pattern:

     # Idle auto-leave: if the meeting has been at "only me + bot" or
     # "only the bot" for IDLE_LEAVE_MINUTES, leave cleanly. This catches
     # the "test call with just me" case that the mass-exit rule misses
     # (peak is 2, so 30% of peak is 0 — never triggers). Tunable via
     # IDLE_LEAVE_MINUTES in the environment.
     IDLE_LEAVE_SECONDS = int(os.environ.get("IDLE_LEAVE_MINUTES", "5")) * 60

     New state in wait_until_meeting_ends

     Add two timestamps next to the existing low_streak counter, both
     initialised to None:

     idle_since_ts = None   # first poll at which the "idle" condition was true

     New checks inside the poll loop

     Inserted after the existing get_participant_count block, before the
     mass-exit low_streak check, so the more-specific rules fire first:

     # Idle auto-leave: only me + bot (count == 2) or only the bot
     # (count == 1). Track how long the count has stayed in the idle
     # zone; once IDLE_LEAVE_SECONDS elapses, leave cleanly.
     is_idle = count in (1, 2)
     if is_idle:
         if idle_since_ts is None:
             idle_since_ts = time.time()
         elif time.time() - idle_since_ts >= IDLE_LEAVE_SECONDS:
             mins = int((time.time() - idle_since_ts) // 60)
             print(
                 f"Idle threshold reached ({mins}m, count={count}, "
                 f"peak={peak_count}) - leaving."
             )
             leave_meeting(page)
             return
     else:
         idle_since_ts = None

     Notes:
     - is_idle is only computed when count is not None. If the participant
     count is unparseable for a poll, the timer is left alone — better to wait
     out the full idle window than to reset it on a transient scrape miss.
     - The mass-exit low_streak block is unchanged and still runs after this,
     so a 20-person meeting that drops to 1 still leaves on the existing path.
     - peak_count is still updated by the existing line above, so the mass-exit
     heuristic continues to see the true peak.
     - leave_meeting(page) reuses the existing helper (lines 163-182).

     Why count in (1, 2) and not "count <= 2"

     A 3-person meeting (you + 2 others) where both leave simultaneously will
     briefly read count=1. With count in (1, 2), that poll would start the
     idle timer, but the next poll would either see 0 (still in the set) or
     the bot is alone. In a real meeting, count=3 (or higher) resets the
     timer on the very next poll, so the false positive window is one poll
     interval (15s) — short enough to be safe, long enough that a stuck-at-2
     test call is caught within IDLE_LEAVE_SECONDS + 15s.

     If we want extra safety, we can add a count == 1 check too (only the
     bot) — but the user already said "only the bot" should be its own rule
     that triggers. count in (1, 2) covers both in one branch; the
     behaviour is the same because the timer is what gates the leave, not
     the count value.

     Why a single timer and not two

     A "count==2" call that drops to "count==1" (you left) is a stricter
     condition, not a separate one. Resetting the timer between the two
     would add a 5-minute delay to the "you left too" case. One timer that
     triggers on either condition is the right call.
